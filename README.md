# DeFiMon

A read-only Ethereum, Plasma, Arbitrum, Base and Binance Smart Chain wallet dashboard for current lending positions and liquidation risk. No wallet connection or transaction signing. Qualifying Cookbook snapshots are stored in public JSON.

## Current scope

Binance Smart Chain uses network key `bsc`, chain ID **56**, native **BNB** and optional server setting `BSC_RPC_URL` (public default `https://bsc-rpc.publicnode.com`). Wallet scans include the existing 750 BSC contracts from `config/token-matches.json`, verified Aave reserve underlyings, wallet-held wstETH and Pendle PT/YT. Existing manual token matches retain priority for cross-network recommendations. `BSC_ARCHIVE_RPC_URL` optionally supplies historical savings-token reads. Run `npm run check:bsc -- 0xWalletAddress` for a network-only check.

BSC lending positions and alternative markets cover **Aave v3, Fluid, Euler V2 and Lista DAO**, plus **Pendle** wallet holdings and Merkl rewards. Morpho core is deployed on BSC, but its public lookup API rejects chain ID 56; Morpho BSC holdings and alternative discovery are explicitly unsupported, as on Plasma. Aave v4, Compound and Spark are excluded from the BSC reader roster. No Ethereum deployments are reused as a fallback. RPC failure leaves BSC balances unknown while other networks remain independent.

BSC deployment provenance: `bgd-labs/aave-address-book@266429e` (`AaveV3BNB.sol`); `Instadapp/fluid-contracts-public@404d73f` (`deployments/bnb` resolvers); `euler-xyz/euler-interfaces@0ea27dc` (`addresses/56/CoreAddresses.json`); `morpho-org/sdks@56f1ed6` (BSC core, reserved for future discovery support); Pendle `56-core.json` at the existing pinned revision. Public RPC checks verified the Aave pool, Euler registry, Fluid vault/fToken discovery and deployed Pendle oracle on 2026-11-20. The reference wallet completed all BSC readers without errors; a WBNB/USDT search returned Aave, Fluid and Euler alternatives with verified rates and liquidity. Pendle's public BSC catalog returned 43 markets.

This is an **early implementation with readers for nine lending protocol families**. Coverage is limited to the versions and products below; it is not a complete wallet balance. Production build and deterministic tests run locally. Fluid and Aave v4 have been exercised against live Ethereum positions; Aave v3 and Compound still require live position comparisons before use for financial monitoring.

## Curve LlamaLend

Deployment and ABI provenance: [curvefi/curve-llamalend.js at d472168](https://github.com/curvefi/curve-llamalend.js/tree/d472168015e5e5db8a565a91fcedf224620dad8a). Ethereum factories: v1 `0xeA6876DDE9e3467564acBeE1Ed5bac88783205E0`, v2 `0x8f6B56EC5ddF1F2691a1059f1D3cd97Ac9EaB0bd`. Arbitrum v1: `0xcaEC110C784c9DF37240a8Ce096D352A75922DeA`. Discovery enumerates these on-chain factories at the wallet snapshot block and verifies vault/controller/token identities. Official SDK and current Prices API publish no Base, BSC or Plasma LlamaLend factory; recommendations label these as not deployed when a matching token search reaches those chains. New deployments need verified configuration, not Ethereum-address fallbacks.

Borrow APR uses the AMM per-second rate × 365 days. Vault lending APR multiplies that rate by debt / total assets, after v2 admin percentage. Borrowable liquidity excludes collateral in LLAMMA and subtracts reserved admin fees and remaining borrow-cap limits on v2. Loan collateral earns intrinsic token yield separately, never the lending vault APR. Soft-liquidated collateral converted into the borrowed token remains part of supplied value. Gauge and wallet shares are converted together once and receipt tokens excluded from wallet value. Rates and balances stay unknown if verification fails.

Recommendations match contract addresses through `config/token-matches.json`. They omit controllers disabled by Curve's frontend and v1 markets created after its 2025-11-12 deprecation cutoff. Creation metadata comes from `prices.curve.finance`; balances, rates, identities and liquidity come from RPC. Missing metadata suppresses v1 recommendations without hiding existing holdings. Curve health percentage is shown in position notes; band-dependent liquidation has no invented fixed LLTV or Aave-style health factor. Liquidity and utilization alert readers support discovered positions.

Live checks on 2026-11-26 enumerated 56 Ethereum markets and 25 Arbitrum markets, including Ethereum v1/v2 and Arbitrum v1 native APR/liquidity quotes. Repeat with `npm run check:curve -- ethereum [0xWallet]` or `npm run check:curve -- arbitrum [0xWallet]`; configured RPC providers are preferable to throttled public endpoints.

Automatic GitHub Pages deployment and a Render server blueprint are included. Follow [DEPLOYMENT.md](DEPLOYMENT.md) to enable Pages, create the server, and connect its public URL. Provider keys stay on Render; the GitHub page cannot run wallet lookups by itself.

## Run locally

Requires Node.js 24 and npm. Use the existing checkout; cloud tasks are already isolated and do not need an additional Git worktree.

```sh
cd /workspace/DeFiMon
npm ci --cache /workspace/.npm-cache
cp .env.example .env
npm run dev
```

Copy `.env.example` only when `.env` does not already exist. Set `ETHEREUM_RPC_URL` in `.env` to an Ethereum mainnet HTTPS provider. The example public provider has no API key and may throttle requests. A dedicated provider is preferable for regular use. Keep provider credentials on the server; never use a wallet key or seed phrase.

The local Vite server uses port 5173 and forwards `/api` to port 3001. For a built version:

```sh
npm run build
npm start
```

The production server serves both the website and API on `PORT` (default 3001). `/api/health` checks the web server and configuration presence; it does not prove Ethereum access. An actual wallet request is required to validate the connection.

## Plasma support

Enter your wallet address and select **Check wallet** to read **Ethereum, Plasma, Arbitrum, Base and Binance Smart Chain together**. Results are grouped by protocol, with networks in that order within each group. Ethereum checks all nine lending families; Plasma checks Aave v3, Fluid and Euler; BSC also checks Lista DAO; Arbitrum and Base check Aave v3, Morpho, Compound, Fluid, Euler and Spark; Arbitrum also checks Curve LlamaLend. Pendle and wallet token balances are checked on all five networks. Each card labels its blockchain. No network selector is needed.

The summary totals add priced positions from all five networks. Collateral, health factors, and liquidation estimates remain independent for each position; collateral on one network never protects borrowing on another. Each network has its own displayed block and check time. Refresh updates all networks for the displayed wallet. If one provider fails, other networks remain visible and the failed network shows unknown balances. Example mode is explicitly fictional and includes empty Base and BSC accounts without changing its sample totals.

Plasma uses chain ID **9745** and native currency **XPL**. The public `https://rpc.plasma.to` endpoint is the default. To use your own provider, add `PLASMA_RPC_URL=https://your-provider` to your existing `.env` file (or your host’s environment variables). Keep your existing `ETHEREUM_RPC_URL` for Ethereum; do not replace the whole `.env` file. Restart the server after changing it. No wallet connection or signing key is required.

Both Plasma readers show current deposits, debt, net value, health, and applicable liquidation estimates with the same coverage limits as Ethereum. Aave efficiency mode retains its native health factor but withholds per-asset liquidation prices. Fluid covers T1–T4 vault NFTs and ordinary lending fTokens; smart vaults show a liquidation oracle ratio. Fluid uses Plasma’s Aave oracle for USD valuation, mapping native XPL to WXPL. For standard T1 borrowing positions, missing collateral USD prices can be estimated from Fluid’s liquidation ratio and an independently sourced debt-token USD price. These prices are labeled “Fluid oracle estimate,” the reader is marked partially checked, and supplied/net totals include the estimate. This is a protocol valuation, not a market-sale quote. The fallback does not assume stablecoin parity, replace available independent prices, or apply smart-pool share ratios to underlying assets. Without a valid ratio and a known debt-token price, quantities and oracle-based risk remain visible with unknown dollar values. Ethereum’s Chainlink registry is never queried on Plasma.

Deployment sources: [Aave Plasma address book](https://github.com/bgd-labs/aave-address-book/blob/main/src/AaveV3Plasma.sol) and [Fluid Plasma deployment artifacts](https://github.com/Instadapp/fluid-contracts-public/tree/404d73f91e6806f881f8dabeb30494f93f9e99b7/deployments/plasma). The used Fluid resolver interfaces were compared with the pinned Ethereum ABIs and match. A provider reporting another chain ID is rejected before reading protocols.

Run a live local check with a public wallet address:

```sh
npm run check:plasma -- 0xYourWalletAddress
```

The website requests `/api/portfolio/0xYourWalletAddress?chain=all`, which returns nineteen protocol/network readers in display order and a separate `networks` snapshot for each chain. A failed network has no block number and explicit error cards; it is not a verified empty wallet. Per-network API access remains available with `chain=ethereum`, `chain=plasma`, `chain=arbitrum`, or `chain=base`; omitting `chain` continues to use Ethereum for compatibility. Health reports configuration presence, not successful blockchain access.

Validation: deterministic reader, network-routing, provider-selection, and browser checks cover Plasma. This cloud environment denied access to `rpc.plasma.to` (CONNECT 403), so a live Plasma wallet comparison is still required on a computer or host that can reach the provider. No cloud environment settings have been published by this change.

## Arbitrum support

Arbitrum One uses chain ID **42161** and native **ETH**. The default public connection is `https://arb1.arbitrum.io/rpc`; no extra key is required. Optionally add `ARBITRUM_RPC_URL=https://your-provider` to your existing `.env` or hosting settings, then restart the server. Keep the other network settings.

Arbitrum includes Aave v3 deposits/borrowing, Fluid T1–T4 vaults and ordinary fToken deposits, Morpho Blue direct markets and V1/V2 vault deposits, and Compound v3’s USDC, USDC.e, USDT, and WETH markets. These readers include USD valuation where prices are available, net value, current interest rates, and applicable liquidation risk with the same product limits as Ethereum. Morpho queries use chain 42161 and validate against Arbitrum’s own canonical core (`0x6c247b1F6182318877311737BaC0844bAa518F5e`), rather than Ethereum’s core. Fluid uses Arbitrum’s Aave oracle for available USD prices, including wrapped ETH for native ETH; its labeled collateral-price fallback follows the Plasma rules above. Missing prices remain unknown.

Wallet ETH and supported Arbitrum tokens appear after Ethereum and Plasma in **Wallet tokens**, contributing to Net value. Supported lending receipts are excluded to prevent double counting. Additional token contracts can be entered for Arbitrum too.

Deployment sources: [Aave Arbitrum address book](https://github.com/bgd-labs/aave-address-book/blob/main/src/AaveV3Arbitrum.sol), [Fluid Arbitrum artifacts](https://github.com/Instadapp/fluid-contracts-public/tree/404d73f91e6806f881f8dabeb30494f93f9e99b7/deployments/arbitrum), [Morpho SDK deployment addresses](https://github.com/morpho-org/sdks/blob/56f1ed62827a7aab39d979c0143d1fbf970c37ca/packages/morpho-ts/src/addresses.ts), and [Compound Arbitrum deployments](https://github.com/compound-finance/comet/tree/f766f51583c23acc33b2a7824654ef2029a96804/deployments/arbitrum). ```sh

Deterministic tests cover all four readers, selected-chain contracts, balances/rates/risk, receipt exclusions, wrong-chain rejection, partial failures, and the combined page. ## Euler V2 EVK

The dashboard now checks **19 protocol/network readers**, including Euler on Ethereum, Plasma, Arbitrum and Base. Euler contracts and selected ABIs are pinned to `euler-xyz/euler-interfaces@0ea27dcf23c31249857180a0753638c040c4df1b`. Core accounting was checked against `euler-vault-kit@93a1de491531e54cbbcf0e5c8cacfe558f924867` and the official EVK periphery lens/math references. No Euler API, subgraph key or new external host is required; reads use each configured network provider at the displayed block.

The registry scan checks direct deposits held by the entered address in up to 4,096 factory EVaults. When the entered address is the registered EVC owner, its 256 same-prefix subaccounts are checked for enabled controllers and collateral. If the address is a subaccount owned by another address, only that entered account is checked. Each account's loan is isolated; collateral never protects debt in another account. A main-account receipt included in a loan is not included again as a passive deposit. Registered Euler receipt tokens are excluded from wallet token totals even if Euler's position reader fails. Failed registry pages, balance reads or missing account checks leave complete coverage unknown and block a complete NPL.

Balances use `balanceOf` → `convertToAssets` and current rounded-up `debtOf` amounts. Borrow APR is the instantaneous per-second ray rate annualized without compounding using Euler’s own 365.2425-day year; supply APR weights it by utilization and deducts the vault's interest fee. Current `LTVLiquidation` captures the vault's time-varying LTV ramp. Health uses `accountLiquidity(account, true)` from the debt controller. Dollar prices use the existing verified price readers; missing prices can use a labeled Euler oracle quote only when the controller explicitly uses Euler's USD unit of account (`0x...0348`, 18-decimal quotes). A missing route or feed stays unknown. Dollar liquidation scenarios are withheld when display-price collateral capacity differs by more than 5% from native oracle health, or a required factor is missing. Native health still determines the risk label.

Euler deposits and loans participate in Recommendations with the existing manual/automatic cross-network token matching. Alternative loans require the exact underlying pair and an accepted collateral receipt vault with a nonzero borrowing LTV. Current supply/borrow interest rates, live liquidation LTV, receipt route and borrowing liquidity are included. Loan alternatives show separate borrowing-vault and collateral-vault links with their contract addresses. Euler loan alternatives also show **Borrow APY** beneath **Borrow APR**, using the same block and Euler’s compounded formula `(1 + per-second rate) ^ 31,556,952 − 1`. A quote near 6.93% APR can therefore match about 7.18% APY on Euler’s own page. APR remains the basis for comparisons and `APR / 12` monthly NPL; APY is separately labeled and is not substituted into those calculations. Available liquidity is vault cash bounded by the remaining borrow cap; Euler's compact 16-bit cap is decoded in raw asset units, with raw zero meaning unlimited and zero-mantissa/nonzero-exponent meaning a real zero cap. Custom borrow hooks and custom collateral deposit hooks are excluded from loan alternatives because eligibility cannot be verified without an execution context. External Merkl incentives are not guessed for Euler alternatives. All recommendations remain read-only rate comparisons.

This integration covers **EVK**, not legacy Euler V1 or Euler Earn strategy aggregators. Passive deposits in subaccounts without enabled collateral/controller, operator-linked smart wallets, and non-EVK collateral wrappers are outside the discovery/valuation scope. These exclusions are shown in the Euler card coverage. No history or transaction submission is required.

```sh
npm run check:euler -- 0x5929D94eb4C41D91955154465a58a531Ad4CF7b8 ethereum
npm run check:euler -- 0xWalletAddress arbitrum
npm run check:euler -- 0xWalletAddress plasma
```

The live Ethereum check at block **26422107** completed a registry/main-account scan for the test address and found no covered Euler positions. A live Ethereum market search at block **26422150** returned **109 alternatives**, including 13 accepted collateral/debt routes; individual read failures were reported as partial coverage. Subaccount loans, share conversion, rates, receipt exclusions, oracle failures, LLTV, NPL and market search are covered by deterministic tests on all four network configurations. A later live Arbitrum rate check at block **524790049** verified **EVK Vault eUSDC-2** (`0x6aFB8d3F6D4A34e9cB2f217317f4dc8e05Aa673b`): **6.93555% Borrow APR / 7.18172% Borrow APY** using the same on-chain rate. Plasma live Euler verification remains pending.

## Savings stablecoin intrinsic APR

Supplied assets marked **Savings stablecoin** in `config/token-matches.json` receive a separate past-month intrinsic rate across supported protocols and networks. The formula is **(current oracle rate − rate 30 days ago) × 365 / (30 × rate 30 days ago)**. This component adds to protocol Supply APR and matched Merkl supply rewards once, then enters asset monthly earnings, position/protocol NPL, Total NPL and recommendation supply rates through the existing calculations. Plain wallet-token balances are not newly assigned monthly earnings.

Verified sources are configured in the `_intrinsicOracles` lists in `config/token-matches.json`; source identity is matched by network and contract, never by symbol. reUSD uses its verified reUSD/USD NAV adapter, and sUSDS/sDAI/sUSDe use the on-chain canonical redemption rate. Source details show the correct token, oracle/contract, observation dates and observed rates. Missing or invalid old data remains unknown and cannot silently contribute zero earnings. Existing token balances, USD prices and liquidation risk stay separate from this return estimate. See [config/README.md](config/README.md#savings-token-oracle-sources) for source discovery, validation and archive-provider requirements.

## Dashboard sections

Below the shared wallet search, the desktop layout has a left navigation column and a right content column. **Wallet Overview** is selected initially and contains the existing balances, NPL/APR totals, risk, protocols, wallet tokens and Merkl rewards. **Recommendations** shows current lending positions as `Supplied asset — Supply APR — Borrowed asset — Borrow APR`, with protocol, network and original loan labels. Personal Morpho V1/V2 vault deposits greater than zero appear as `Supplied asset — Supply APR`; managed vaults with zero personal deposits are omitted. Other one-sided lending positions show a dash for the absent side.

Fluid vaults with exactly the same two distinct token contracts supplied and borrowed (for example Plasma Vault 33 GHO/USDT0 against GHO/USDT0) are excluded from Recommendations, do not generate alternative-search requests, and are excluded as Fluid alternative candidates. Token order and capitalization do not affect this rule; token symbols alone are not used. Other Fluid positions remain eligible. Wallet Overview, balances, risk and NPL still include these vaults.

Rates reuse the same protocol, intrinsic and matched Merkl components as Wallet Overview. Unknown active rates stay unavailable. Multi-asset loans show asset combinations inside that loan; assets are never paired across unrelated positions, protocols or networks. Below each existing position, live alternative markets are ranked by lower Borrow APR or higher Supply APR as described below. Switching sections preserves overview scenario inputs and does not change totals; the first Recommendations visit for each wallet snapshot starts an independent market search. A new wallet search or refresh updates both sections from the same response. On smaller screens the menu moves above the content, with wide tables scrolling inside their cards.

## Alternative-market recommendations

Recommendations independently searches the supported market deployments for the same supplied/borrowed token pair. It lists strictly lower **Borrow APR**, ordered by Available Liquidity from highest to lowest, with unavailable liquidity last and lower Borrow APR breaking liquidity ties. The Best verified Borrow APR summary still identifies the cheapest verified rate, independently of row order. For Morpho vault deposits and other supply-only positions, it lists strictly higher **Supply APR** for the same deposited token, including other Morpho vaults and direct lending markets. Each alternative identifies its protocol, network, contract/market, snapshot block, rate difference in percentage points, LLTV for loans, and an app link. The current market is excluded; Aave v4 hub/reserve routes remain distinct. Multi-asset Fluid pools qualify only if all of their required supply and debt underlyings are present in the source position's token basket.

- Aave v3: current main-pool reserves on Ethereum, Plasma, Arbitrum, Base and Binance Smart Chain, with active/frozen/paused, collateral, borrowing and isolation-eligibility checks. Quotes use standard variable borrow rates, not a guessed wallet-specific eMode or discount.
- Aave v4: the 14 supported Ethereum lending Spokes and 37 tokenized deposits. New single-collateral loan estimates include the reserve's risk premium; existing multi-collateral or stored premium shares can differ.
- Compound v3: the supported Ethereum USDC/WETH and Arbitrum USDC/USDC.e/USDT/WETH deployments. Only the base token can be borrowed; configured collateral, supply caps and supply/withdraw pause flags are checked. Collateral protocol supply APR is zero.
- Morpho: Ethereum, Arbitrum and Base Blue markets, vault V1 and vault V2, discovered by token address with bounded pagination and then checked using the actual core/factory/underlying contracts. Instant IRM and allocation-weighted, fee-adjusted vault rates reuse the existing on-chain rate readers. Morpho Plasma and BSC discovery are unsupported by the public API.
- Euler: V2 EVK vaults and accepted collateral/debt pairs on Ethereum, Plasma, Arbitrum, Base and Binance Smart Chain; receipt routes, current fee-adjusted interest and capped borrowing liquidity.
- Fluid: T1–T4 vaults and ordinary fToken deposits across the three supported networks, using the published resolver registry and existing per-token rate readers. Smart-pool rates exclude trading income and retain their full required asset basket.

Loan alternatives show **Available Liquidity** immediately after Borrow APR, in units of the destination market's debt token (for example GHO or USDT0). It is independent of the wallet's personal collateral capacity. Each amount uses the same network block as its rate quote. Aave v3 uses reserve cash capped by virtual liquidity and remaining borrow-cap headroom; minting GHO reserves instead use remaining facilitator capacity. Aave v4 uses Hub liquidity capped by the specific Spoke's remaining draw capacity, including owed debt and deficit. Compound uses the Comet's base-token cash. Fluid T1/T2 uses resolver-reported underlying borrowable capacity; smart-debt T3/T4 converts proportional shares into both debt tokens and limits them by vault/pool caps, per-token liquidity and utilization headroom. Smart-debt values are explicitly estimates requiring the paired token. Morpho shows **Total liquidity**: accrued total supplied loan assets minus accrued total borrowed loan assets, not collateral TVL or total supplied deposits. Verified zero is displayed as zero; unreadable amounts/decimals remain **Unavailable** and do not remove an otherwise verified rate recommendation. No dollar peg or balance approximation is used to invent liquidity.

Token matching uses exact contract addresses on the same network and the manually editable [config/token-matches.json](config/token-matches.json) across networks. It contains the CoinMarketCap EVM snapshot, explicit savings examples and the user's manually maintained token groups. Optional `_category` metadata marks Stablecoin, Savings stablecoin or Other; it is excluded from address matching. Other EVM chain addresses can be stored, while recommendation searches stay on Ethereum, Plasma, Arbitrum and Base. Ethereum USDT, Plasma USDT0 and Arbitrum USDT are explicitly matched in the USDT group. USDC.e is not mapped to native USDC. Only networks explicitly listed in a manual group are matched for that group; omitted entries remain omitted. Unlisted source contracts are automatically looked up through CoinGecko and, when its server key is configured, CoinMarketCap. Discovery verifies the original network/contract and reads other platform addresses from the same asset record; both assets of a pair still need a verified match on the destination network. If lookup fails, the original-network search remains available. Similar API tickers and wallet-token-catalog symbols are never used as identity proof. Manual groups always win, including omitted networks. Automatic links into existing manual groups or conflicting provider identities are excluded. Recommendations shows provider links and matched contracts under Token matching. Automatic groups are cached only in memory and never written into the JSON file. See [config/README.md](config/README.md) for how to add groups and restart the server; JSON edits do not require a build. Invalid addresses, unsupported network names and duplicate network/address identities are rejected at startup. Native Fluid ETH is normalized to its wrapped equivalent, so wrapping or bridging may be required.

Current rates retain the wallet's matched Merkl incentives. Candidate rates include protocol fees/streaming adjustments and the same verified intrinsic token yield, but exclude unverified external Merkl campaigns. This conservatively compares a candidate borrowing rate against the wallet's effective net borrowing cost, rather than promising rewards for a position the wallet has not entered. Comparisons do not alter NPL, balances, or risk. Rate snapshots do not guarantee capacity for the full existing loan/deposit, account access, caps, bridge availability or migration costs; those details are stated with each candidate. Empty/unreadable rates are not treated as zero, and no-better-result messages refer only to verified search results.

`POST /api/recommendations` accepts only bounded token/network targets, not a provider URL or wallet credentials. Searches run separately from wallet monitoring with two concurrent searches per server; each source has independent failure/coverage reporting. Up to 40 asset combinations, 500 Morpho records per query family, and bounded RPC worker time are checked. Partial or failed sources remain labeled and do not block verified alternatives or wallet totals. Responses are not stored as wallet history. ## Collateral LLTV and liquidation scenarios

Every protocol asset table includes **LLTV**: the percentage of collateral value counted toward the liquidation boundary, rather than the maximum initial borrowing limit. Aave v3 uses its liquidation threshold; Compound uses `liquidateCollateralFactor`; Morpho uses the market LLTV; Fluid uses the vault liquidation threshold; Aave v4 uses the wallet’s stored collateral settings. Aave v4 combines same-token reserves using the effective balance-weighted factor, excluding disabled collateral, and labels it accordingly. Morpho displays actual market LLTV even when lent and pledged balances of the same token are merged. Deposits that are not pledged show a dash. Unverified effective LLTV shows **Unavailable**, never a guessed percentage. Modern Aave v3 efficiency-mode LLTV is read from category settings and verified reserve bitmap membership; older/incompatible deployments remain unknown. Efficiency-mode token liquidation estimates continue to be withheld.

For a loan with two or more supplied collateral assets, the table calculates a liquidation price for **only the largest holding by current supplied USD value**. Enter a non-negative USD liquidation price for each other collateral token in its row, then press **Calculate**. For three assets the calculation is:

```text
price_1 = (borrowed_USD - price_2 × LLTV_2 × supplied_2
                        - price_3 × LLTV_3 × supplied_3)
          / (LLTV_1 × supplied_1)
```

Percentages are converted to fractions (80% = 0.8). The same sum extends to any number of collateral assets within that loan. Borrowed USD, supplied quantities, and effective factors stay fixed, including any debt denominated in a collateral token. This is a scenario based on your entered prices; it does not predict that the tokens will reach those prices together or change the current health factor, balances, or net value. A single-collateral loan retains its existing estimate, including its existing same-token debt treatment.

All other collateral prices must be entered before a result is calculated. Editing a price clears the previous result; refreshing or loading another wallet clears all inputs and results. Zero is allowed. If the other collateral alone exceeds the fixed borrowed USD amount, the result explains that there is no non-negative price boundary rather than displaying a negative token price. Missing debt valuation, collateral prices needed for ranking, or effective LLTV prevents calculation. Independent loans, networks, and protocol positions are never combined for liquidation calculations. Manual prices stay in the open page and are not sent to a server or saved.

Fluid smart collateral/debt uses pool-share oracle rules. Its collateral rows display the vault LLTV, but independent token-price calculations remain unavailable; the existing oracle-ratio boundary is retained. Missing or unsupported liquidation rules are identified explicitly.

## Current interest rates

Every supplied/borrowed asset row has **Supply APR** and **Borrow APR**. APR is the current interest rate expressed per year, without assuming compounding. Protocol rates refresh with the wallet and use the same selected network block as its balances. sUSDai additionally shows a separately labeled past-month intrinsic estimate from an Ethereum oracle, with its own reference block and observation dates (see below). These are current quotes, not past-day averages or a promise of future returns. The example’s rates are fictional.

A dash means that the wallet has no balance on that side. **Unavailable** means a current rate could not be verified; balances and liquidation risk remain visible. A genuine zero-interest rate shows **0.00%**. **≈** marks an estimate or an incomplete income component; open **Rate details / Estimate details** beside the rate for its scope. Negative supply APR means a charge; negative borrow APR means a net incentive within the quoted components. Cash wallet balances have no lending APR merely because they are held.

- **Aave v3, all five networks:** current liquidity APR and the wallet’s balance-weighted variable/stable borrowing APR. Annual ray rates are divided by 1e27. Stable borrowing uses the wallet’s own stable rate; the reserve supplies the variable rate. Reward-token incentives are excluded.
- **Aave v4:** current Hub drawn-rate quotes, accrued drawn index, added assets, premium shares, liquidity fee, and virtual assets determine supply interest. Borrowing APR includes the wallet’s stored premium-share exposure on total debt. The same underlying across reserves is weighted separately by supply and borrow balances; a missing active component keeps the aggregate rate unknown. Tokenized deposits use the same Hub supply APR. Reinvestment income and external reward tokens are excluded; swept capital and effective debt quotes are labeled estimates.
- **Compound v3:** base-token rates use utilization read after simulated current-block accrual. Rates per second are annualized over 365 days. Collateral assets earn zero protocol supply interest; their intrinsic yield and COMP incentives are separate.
- **Fluid, all five networks:** ordinary vault legs use signed `supplyRateVault` / `borrowRateVault` after vault adjustments (100 = 1%). Smart legs combine each underlying token’s interest-bearing Liquidity rate with the signed vault adjustment. Their trading income cannot be calculated from an instant snapshot, so the displayed interest component is labeled an estimate. Lending fTokens use modern total-holder APR where supported, otherwise the exact legacy resolver layout with separately converted bonus units (1e12 = 1% for the legacy streaming model). An incompatible layout is rejected rather than misread.
- **Morpho Blue:** the IRM is queried in the same read-only simulation as accrual, using the resulting market state, so adaptive model state is current and a past accrual interval’s average is not substituted. The per-second borrow rate is annualized; supply APR includes utilization and the market fee. Unlent collateral earns no protocol interest. Same-token lent/collateral quantities are weighted correctly. Incentives and intrinsic token yield are separate.
- **Morpho vaults:** V1 estimates weight current market lending APRs and idle cash and subtract the performance fee. V2 estimates support direct-market adapters and V1-vault adapters, with current allocation checks, the distribution cap, and enabled performance/management fees. An unsupported funded adapter or an unreadable allocation makes the rate unavailable. No historical APY is substituted. Independently matched Merkl incentives are shown as a separate component rather than changing the protocol quote.

Rate checks have deterministic coverage for units, weights, fees, adaptive-state simulation, true zero, negative adjustments, and missing data. Live Ethereum checks at block 26408160 read Fluid smart-leg rates, a Morpho market’s current rates, a V1 vault allocation estimate, and an interest-free Aave v4 Hub. Plasma and Arbitrum remain blocked by this cloud’s network policy; local live comparison is still needed. Rate reading needs no new API key or outbound destination beyond the existing network providers.

## Monthly interest and NPL

Every supplied/borrowed asset row shows **Monthly interest earned** and **Monthly interest paid**, in token units and in USD where a price is known. Calculations use full-precision values before display rounding:

```text
monthly earned tokens = supplied tokens × supply APR / 12
monthly paid tokens   = borrowed tokens × borrow APR / 12
monthly USD amount    = monthly token amount × current USD price
monthly NPL           = total monthly interest earned USD − total monthly interest paid USD
```

APR values are fractions (6% = 0.06). Monthly calculations use the same effective APRs displayed in the asset row: supply APR includes intrinsic yield and verified Merkl incentives once, while borrow APR subtracts verified Merkl rebates. Supply and borrow rates can be signed: a negative earned amount is a supply charge; a negative paid amount is a borrowing incentive/credit. Zero-interest collateral earns zero protocol interest.

Each non-Fluid protocol/network card shows its combined **Net value**, followed by **Monthly NPL** and the earned/paid USD breakdown, summing every checked position in that card. Fluid shows NPL separately inside each vault position; ordinary fToken lending deposits each have their own NPL too, with no Fluid-wide NPL displayed. The fourth portfolio summary card, **Total NPL**, replaces the former Lowest health factor card and sums all protocol/network positions, counting each Fluid vault and lending deposit once. It includes sUSDai intrinsic yield where available and excludes ordinary wallet tokens. A failed protocol reader or unknown active interest component makes the complete total unavailable; partial coverage is labeled when only checked positions can be included. The summary cards appear after loading a wallet or the illustrative example. Health factors remain visible for individual positions. Networks and unrelated protocols remain independent. NPL means the projected net monthly interest result; it does not include token-price gains/losses, gas, liquidation charges, or other unlisted fees/rewards, and it does not change current Net value or health.

Every lending position shows **Supplied → Borrowed → Net value → Monthly NPL → APR → Health factor**. Position Monthly NPL uses the same earned-minus-paid calculation as its APR, including matched rewards and intrinsic yield, with negative values retained and missing inputs labeled Unavailable. This is a display of the existing calculation and is not added to totals a second time.

Morpho V1/V2 vault deposit cards use a supply-only table: **Asset**, **Supplied**, **Supply APR**, **Current price**, and **Monthly interest earned**. Vault cards omit Borrowed and Net value; direct Morpho borrowing-market cards retain their lending and risk fields. Monthly token interest is `own supplied tokens × combined Supply APR ÷ 12`; its USD equivalent uses the current token price and enters Total NPL exactly once through the existing protocol total. The combined rate includes verified intrinsic yield and matched Merkl supply incentives. Creator/owner/curator roles do not turn vault-wide assets into personal deposits or earnings. A zero personal deposit contributes zero, even if its APR or price is unknown; an active deposit with a missing rate or required price remains unavailable.

Personal balance discovery and vault-management discovery are tracked separately for Morpho. If all three personal lookups (markets, V1 deposits and V2 deposits) finish without coverage warnings, failed creator/curator/owner listing queries do not invalidate those personal balances or block NPL. Management-query failures remain visible on the Morpho card. An incomplete personal lookup still blocks NPL, even if management queries succeed; unreadable individual positions, active rates and required prices also remain blockers. This covers the reported Arbitrum response where six lookups succeed, all personal holdings are empty, and only the two V2 role queries are rejected. Those empty personal holdings contribute zero, while V2 role coverage remains unknown.

The overview shows the readable NPL subtotal even when some chains, protocols, tokens, prices or rate components cannot be checked. **Total NPL · partial** is known monthly income minus known monthly costs; unknown components are explicitly excluded, and the complete result may differ. **Portfolio APR · partial** uses this known monthly NPL × 12 ÷ the displayed checked Net value. A **Missing interest data** explanation lists the incomplete protocol, network, position and token checks. Nothing is silently presented as a complete total; missing active amounts remain unavailable at their original rows. If no active interest component can be verified, NPL and APR remain unavailable. Genuine zero and negative subtotals are retained.


This checks native lending interest and intrinsic yield across the configured networks, prints the missing inputs, and excludes Merkl incentives. It does not print provider URLs, keys or `.env` contents. Cloud network restrictions can differ from those on the host computer; a cloud lookup cannot establish which source failed locally. The page's explanation uses its currently displayed data, including any applied Merkl APR.

A fifth overview card, **Portfolio APR**, appears directly after Total NPL. It uses `Total monthly NPL × 12 ÷ displayed Net value`, expressed as a percentage. The denominator includes the same priced wallet tokens, supplied assets and debt as the Net value card; it is not limited to lending equity. It includes Merkl and intrinsic yield through Total NPL once, uses unrounded values, and follows the same zero/unknown/nonfinite and signed-negative-value rules as position APR. Partial coverage is labeled. For the supplied example, $1,054.76 monthly NPL and $280,096.14 Net value produce approximately **4.52%** annually.

Each position’s summary shows **APR** between Net value and Health factor, calculated as `Monthly NPL × 12 ÷ Net value` and displayed as a percentage. Protocol totals use their combined monthly NPL and net value; Fluid vaults and lending deposits use only their own amounts. The calculation includes any intrinsic yield and matched Merkl incentives already included in NPL. Zero or unknown net value, unknown NPL, and nonfinite results show **Unavailable**. Negative net value follows the signed formula and is explicitly labeled, rather than presented as a return on positive capital. This figure is an annualized NPL estimate, separate from an individual asset’s Supply/Borrow APR, and does not change balances or risk.

These are estimates for one-twelfth of a year, assuming unchanged balances, APRs and USD prices, without compounding. They refresh with the displayed wallet. The sUSDai intrinsic component retains its past-month observation basis rather than becoming a guaranteed next-month rate. Missing active rates or required USD prices make the affected position/row totals **Unavailable**, while the portfolio summary still sums its readable components and labels them partial; token interest can still be shown when only its USD price is missing. Zero balances require no rate or price to contribute zero. Explicit unreadable positions prevent a complete total; partial coverage is labeled and any displayed subtotal covers checked positions only. ## sUSDai intrinsic yield

Supplied **sUSDai** includes a separately labeled **Intrinsic (30d)** APR across all protocol families on Ethereum, Plasma, Arbitrum, and Base. Matching uses the deployed token contract `0x0B2b2B2076d95dda7817e785989fE353fe955ef9`, not a token symbol. Other assets and borrow APR remain unchanged.

The source is Ethereum’s [sUSDai/USDai exchange-rate feed](https://etherscan.io/address/0x0fBE44B96320EBD455FF9CCE0781fA9A83Ddee7a#readContract). Its address is the raw rate source in [Fluid’s pinned Ethereum CappedRateChainlink_SUSDAI deployment](https://github.com/Instadapp/fluid-contracts-public/blob/404d73f91e6806f881f8dabeb30494f93f9e99b7/deployments/mainnet/CappedRateChainlink_SUSDAI.json). The reader verifies Ethereum chain ID, feed description and decimals, and valid positive oracle rounds. It never uses the capped oracle’s maximum permitted APR as earned interest.

```text
intrinsic_APR = (end_exchange_rate / start_exchange_rate - 1)
                × seconds_in_365_days / elapsed_seconds
```

“Last month” means a trailing **30-day lookback**, not the previous calendar month. The reader selects the last oracle observation at or before 30 days ago and the latest available observation, annualizing their actual elapsed time. Oracle updates are discrete: the current reading and the old boundary may each lag by up to three days, and accepted observation windows must span 27–33 days. Details show the actual observation dates, source, and Ethereum reference block. The feed’s existing round records are queried at one current block, including previous aggregator phases when necessary; no archive-node subscription, USD.ai API access, wallet history collection, or database is required. Missing/gapped rounds, stale prices, incompatible feeds, or failed provider reads produce **Unavailable**, never an invented zero. No new domain or key is required beyond the configured Ethereum provider.

The supply cell shows **Estimated total APR**, consisting of current protocol lending APR plus this annualized past-month intrinsic return and any separately matched Merkl incentive APR. This is an approximate combination of different observation periods, not a current combined quote, compounded APY, or USD.ai’s advertised dashboard APY. Share-rate performance can include losses and differs from the USD market price or bridge premium. If the protocol or intrinsic component is unknown, the combined supply APR stays unavailable while verified components remain visible. Unverified Merkl incentives are excluded with a notice as described below. Balances, net value, borrowing rates, health and liquidation prices are not changed by the yield estimate.

The oracle quote is shared across protocol/network lookups and cached for five minutes; unavailable quotes retry after one minute. No wallet address is sent to the oracle. Live verification at Ethereum block **26414491** found sUSDai/USDai rates of about **1.11884234** and **1.12579575** over **30.008 days**, yielding an estimated intrinsic APR of **7.5594%**. This is a verification snapshot, not a hardcoded rate.

```sh

```

### Merkl APR adjustments

The same rewards lookup independently reads `GET /v4/users/{address}/rewards/active-opportunities`, then fetches `GET /v4/opportunities/{id}?campaigns=true` for supported campaign rules. APR values returned in percentage points are divided by 100 (1.75 becomes 0.0175). The opportunity’s current `apr` is used, not its `maxApr`, historical earnings, native protocol APR, or a campaign’s target/capped distribution setting. Only live opportunities with a currently active token-reward campaign and verifiable eligibility are applied. Historical unclaimed balances are never added to projected monthly income.

Currently supported matching:

- **Fluid `FLUIDVAULT_COLLATERAL` and `FLUIDVAULT_BORROW`:** require the actual resolver-reported vault contract, network, action and underlying token set to match the checked vault position. Supply rewards increase the supply APR; borrow rewards reduce effective borrowing APR. Each smart-pool underlying receives the side’s APR so total annual rewards equal that side’s USD value × APR. It does not duplicate one pool-side reward on each underlying’s full pool value. Multiple NFTs in the same vault receive the rate on their own balances; another vault, network or fToken deposit does not inherit it.
- **Aave v4 `AAVE_V4_HUB_NET_BORROWING`:** fetch current campaign hub, borrow-asset and supply-asset IDs and underlying contracts. On-chain hub/asset exposures are retained across merged reserves and tokenized deposits. Eligible stablecoin supplies across checked spokes are deducted from eligible borrowing. The net reward value is allocated proportionally across matching debt, giving an effective rebate of `listed APR × max(0, eligible borrowed USD − eligible supplied USD) / eligible borrowed USD`, further weighted when only part of a merged token balance qualifies. Thus 1.75% on a $10,000 loan with $4,000 of qualifying supplies gives a 1.05% effective rebate on gross debt. Incomplete Aave coverage, missing qualifying prices, mismatched identities or unreconciled exposures prevent automatic adjustment. Current balances approximate the campaign’s time-weighted score; the result is explicitly an estimate.

Campaign times, computation chain, opportunity identity, token reward type, whitelist/blacklist rules, and conflicting active eligibility sets are checked. Custom score/subtype methods, hooks, forwarded-account conditions, private/overridden campaigns, unknown campaign types, unsupported reward types and ambiguous or duplicate identities are not guessed. Those opportunities remain listed with **Not applied** and an explanation. Discovery is bounded to twelve supported opportunity-rule lookups per wallet, with three concurrent detail requests. Newly opened positions may be absent until Merkl indexes earnings; the user-opportunity endpoint is not a complete list of every campaign a fresh position could qualify for.

Asset rows retain **Protocol**, **Intrinsic (30d)** where applicable, and **Merkl** components and their details. Borrow APR can become negative when the estimated rebate exceeds base interest. Merkl pays rewards separately: the lender still charges protocol interest, and monthly net token amounts are value-equivalents rather than the actual reward-token payout. The displayed NPL assumes unchanged rates, balances and prices; future caps, campaign expiry, qualification and time-weighting can change earnings. Market prices, collateral liquidation rules, health and current Net value are unchanged.

APR lookups can fail independently of reward balances. While loading or unavailable, verified protocol rates remain visible and a notice explains that NPL excludes unverified Merkl incentives. Supported opportunities are applied only to the wallet that was searched, and repeated responses never compound the same APR. User-provided public Merkl outputs confirmed the three example types and identifiers (Aave’s hub net-borrowing campaign and separate Fluid supply/borrow opportunities on Plasma); deterministic and browser fixtures cover their matching and financial calculations. Full live end-to-end verification is still blocked by this cloud’s Merkl network restriction.

USD values use positive numeric Merkl token quotes only when the token is marked verified by Merkl and the quote timestamp is within one hour (allowing five minutes of future clock tolerance). Merkl’s verified flag is a token metadata flag, not an investment-safety assessment. Missing/stale prices keep USD values unknown while preserving token quantities. Fully claimed zero-balance rewards are omitted. A successful empty report means no unclaimed/pending token rewards were reported; connection errors, throttling, malformed responses or unsupported schemas mean **unknown**, never a verified empty wallet. Recent claims and earnings can lag Merkl indexing. An indicated dispute window is shown, and “unclaimed” is not a guarantee that every published reward is immediately claimable. Claiming is handled on Merkl’s own website; this dashboard never connects a wallet or signs a claim.

Reward balances and APR opportunities load through `/api/rewards/0xYourWalletAddress` independently of lending and wallet balance lookups. Wallet searches and Refresh update both; stale/canceled responses cannot replace a newer wallet or the synthetic example. A Merkl outage does not hide lending positions, and a lending-provider outage does not discard successfully read rewards. No wallet searches, rewards history, Merkle proofs or signing keys are stored. The server sends the public wallet address to Merkl, but never provider credentials. ## Calculations

- Net value = supplied value minus debt value. Supplied value already includes collateral; receipt tokens are not counted again.
- All on-chain calls for a wallet use one Ethereum block. Numbers can change after the lookup; refresh manually for a new snapshot.
- Aave uses native account debt and health factor, reserve balances, and its price oracle. The pool, data provider, and oracle are resolved from the official Ethereum addresses provider.
- Compound uses its price feeds and **liquidateCollateralFactor**, rather than the borrowing collateral factor. A single read-only multicall simulates `accrueAccount` before reading base balances. This does not submit a transaction.
- For an individual asset, solve `weighted collateral = debt` while all other prices/balances stay fixed. If that asset is both supplied and borrowed, both sides move with its price.
- Per-asset estimates are scenario calculations, not predictions. A dash means no positive downward boundary can be estimated, no debt, or an unsupported mode. They are not a promise that a position is safe.
- Risk bands: health <= 1 threshold reached; below 1.1 high; below 1.3 watch; otherwise lower. These are display conventions. Protocol rounding, interest, changing prices, and special liquidation rules can affect execution.
- Aave v4 reads each lending Spoke separately: a healthy position in one market does not protect debt in another. Reserve enumeration includes non-collateral deposits. Current underlying balances come from `getUserSuppliedAssets`; debt from `getUserTotalDebt` includes drawn and risk-premium debt.
- V4 account Value units are **USD × 1e26**; `totalDebtValueRay` is **USD × 1e53**; health factor and average collateral factor are **1e18** scaled. These differ from v3. The reader checks that the market oracle uses the required 8-decimal USD precision before converting native USD account totals.
- V4 liquidation estimates use `getDynamicReserveConfig(reserveId, userPosition.dynamicConfigKey)`, not the reserve’s newest configuration key. Repeated underlying assets are merged with enabled-only collateral weights, so price scenarios account for the token appearing on both sides of the position. Native health stays authoritative.
- V4 tokenized-deposit balances use ERC-4626 `convertToAssets` once. A matching reserve for the exact Hub/asset pair supplies the USD oracle price. Deposit-only tokens have no borrowing or collateral liquidation risk. Missing feeds or failed market reads are explicit partial/unknown results, not zero balances.
- V4 estimates assume prices of other tokens, balances, and the current premium debt stay fixed. Future interest, risk-premium changes, user actions that refresh settings, and protocol rounding can change the boundary.
- Fluid discovers vault NFTs using the official VaultResolver and reads each NFT independently. Each NFT has separate risk, even when multiple NFTs use the same vault. Closed NFTs are omitted; balances after liquidation use the resolver’s remaining supply and debt.
- Fluid T2/T3/T4 collateral and debt shares are expanded into underlying tokens using DexResolver per-share amounts from a read-only simulation. Its contracts catch some internal failures and return zeros; all-zero conversion results are treated as unavailable, not zero balances.
- Fluid health = `current supply × liquidation oracle price / 1e27 × liquidation threshold / current debt`, in the resolver’s raw units. This uses the **liquidation** oracle, not the operating oracle or borrowing limit. Tick rounding can affect actual liquidation execution.
- Standard Fluid vaults show a dollar liquidation price assuming the debt token USD price is fixed. Smart vaults instead show current and threshold oracle ratios (debt token or debt pool shares per collateral token or collateral pool share). A pool share quote represents 10^18 raw shares. These are protocol ratios, not a prediction about one underlying token.
- Fluid USD valuations use Aave’s oracle with a Chainlink USD Feed Registry fallback (positive, complete round, no more than 24 hours old at the selected block). Native ETH maps to WETH for Aave pricing. Unsupported prices remain null; stablecoins are never assumed to be worth $1. USD valuation does not determine Fluid’s health estimate.
- Ordinary lending fToken shares are converted once to current underlying assets with `convertToAssets`; they have no borrowing or collateral-liquidation risk.
- Morpho uses the public `https://api.morpho.org/graphql` API only for Ethereum/Arbitrum market/vault discovery and indicative USD prices. Market and V1-vault results are paginated; V2 holdings come from `userByAddress(address, chainId: 1)` (42161 on Arbitrum) and its unpaginated `vaultV2Positions` list. A missing user entity is reported as unknown coverage. Failed queries, incomplete pages, duplicate rows, and malformed/wrong-wallet/wrong-chain records are explicit warnings, not a verified empty wallet. No API key is required. Newly created/changed positions may be missing until indexed.
- Morpho identities and token decimals are rechecked on the selected network. Market parameters are loaded from canonical Morpho Blue (Ethereum `0xBBBBBbbBBb9cC5e90e3b3Af64bdAF62C37EEFFCb`, Arbitrum `0x6c247b1F6182318877311737BaC0844bAa518F5e`) and hashed back to the market ID. A vault must be recognized by the factory reported by the official API; V1 vaults must also point to this canonical core. This verifies data identities, not investment safety or curator quality.
- One read-only multicall simulates Morpho market `accrueInterest` before reading market totals and user shares. Supply conversion rounds down; borrowing rounds up, using 1 virtual asset and 1,000,000 virtual shares. Collateral is counted separately from loan-token supply. Loan supply does **not** protect a borrowing position, even within the same market.
- Morpho oracle prices use **1e36** raw-unit scaling. Health matches the protocol’s two floor divisions: `floor(floor(collateral × oraclePrice / 1e36) × LLTV / 1e18) / rounded-up debt`. A reverting oracle gives unknown risk; a successfully read zero price gives zero collateral capacity, as in the protocol. Currency conversion accounts for both tokens’ decimals.
- Morpho vault shares are valued once, without adding their underlying market allocations again. V1 uses the current ERC-4626 conversion. V2 simulates accrual, then reads the user balance, total shares, stored assets, and virtual shares together so fee-share minting and current interest are included. Vault-only holdings have no wallet borrowing liquidation price.
- Morpho USD prices are indicative API prices and may update at a different time than the pinned network block. They never determine health. Missing prices stay unknown; a token is never assumed to be worth $1. A liquidation USD estimate assumes the loan-token price and both balances stay fixed. The collateral/loan oracle ratio is also shown independently of USD valuation.
- Display calculations use floating-point numbers after decoding integer balances. They are estimates and should not be used for transaction sizing at the liquidation boundary.

### PT collateral Supply APR

For every lending position with supplied Pendle PT collateral, **Supply APR = the current Pendle Implied APY**, using the APY number directly as requested. For example an Implied APY of 15.07% gives a 15.07% base Supply APR. The usual formulas then calculate monthly earned interest (`Supplied × Supply APR / 12`), monthly NPL and annualized NPL/net-value APR, including protocol and portfolio totals. This is a price-accretion estimate toward maturity, rather than a lending interest payment. It does not convert compounded APY into a different APR, add the protocol’s old base supply rate, or add a second savings-token intrinsic yield. Separately matched Merkl incentives retain their existing treatment.

PT identities are matched by exact contract and chain in Pendle’s catalog, then checked using the market’s token addresses and the PT/market expiry at the pinned network block. This applies to PT collateral held inside Aave v3/v4, Morpho, Compound, Fluid or Euler even when the wallet has zero directly held PT. Rates must be timestamped within 30 minutes. Unavailable active PT rates remain unknown; after verified maturity the future accretion rate is zero. Ordinary collateral, YT, deposits without collateral status and borrowed-asset rates keep their existing treatment. Rate details link to the source Pendle market.


### Lido staking APR for wstETH collateral

The same staking return accrues through wstETH’s stETH exchange rate. The API percentage is divided by 100 once; it is already APR and is not converted from APY. It is added once as a separate intrinsic component to protocol supply APR. Existing matched Merkl rewards remain separate. Monthly interest earned, monthly NPL, protocol/position APR and portfolio totals all use that combined supply rate.

Recognition uses exact chain/contract addresses rather than the ticker. ## Wallet token categories and income

Morpho direct-market positions with positive loan-token supply shares, zero borrowing shares and zero pledged collateral use the vault-style deposit display: Supplied, APR and Monthly interest earned, without loan or liquidation fields. The market's accepted collateral remains separate context and is never added as a personal holding. These positions retain their market IDs/links and direct-market Supply APR; recommendations compare higher supply rates for the loan token, and income is counted once in Total NPL. Positions with any pledged collateral or borrowing keep the lending-position display.

Pendle market metrics use the catalog while it is fresh. If APYs/TVL are missing or its snapshot is older than 30 minutes, held active markets are refreshed through Pendle's individual-market endpoint. Refreshes are shared by PT/YT for one minute and must match the exact chain, market, token contracts, units and expiry; stale or mismatched responses remain unavailable. A real zero underlying APY is displayed as 0.00%. PT collateral rates use the same refresh path.

**Wallet tokens** is split into **Interest bearing tokens** first and **Other tokens** second. Each category retains the Ethereum, Plasma, Arbitrum, Base and Binance Smart Chain grouping; tokens within each network/category are sorted by USD value, largest first, with unpriced tokens last. Interest bearing tokens contains all configured Savings stablecoins plus the user-confirmed wallet-held wstETH and Pendle PT. Other tokens includes ordinary stablecoins, native currency, other assets and YT, with no fixed intrinsic wallet income assigned.

Each interest-bearing row shows intrinsic APR and estimated monthly income in token-equivalent and USD units. Savings stablecoins use the **same rate resolver and source quotes as lending positions**: existing sUSDai oracle rounds, or verified 30-day rate/redemption snapshots for other configured savings assets. wstETH uses Lido’s seven-day staking APR. PT uses its verified Pendle Implied APY directly as APR, becoming zero after verified expiry. A source quote already obtained for the same token in a lending position is reused; the lending protocol’s own supply APR is never copied into a wallet holding.

Monthly wallet earnings = **current wallet USD value × intrinsic APR ÷ 12**. Category APR = **sum of monthly wallet earnings × 12 ÷ category USD value**, so it is weighted by current USD value rather than the number of tokens. The category summary spans all five networks and each nonempty network shows its own summary. Receipt/debt tokens excluded from wallet value are excluded from wallet income too; their underlying protocol income is already counted under lending. Other-token price failures do not invalidate verified wallet income, while unreadable yield-token balances, unresolved receipt checks, missing yield rates or missing yield-token USD values remain unknown rather than zero.

**Total NPL = protocol monthly earned interest + interest-bearing wallet monthly earnings − protocol monthly borrowing costs. Portfolio APR = Total NPL × 12 ÷ existing Net value.** Net value continues to count each wallet token once. Pendle tokens displayed in both the Pendle section and Wallet tokens do not add a second value or a second income contribution. No wallet balance history or database is introduced; the figures are current-state estimates using fixed balances, prices and rates. `npm run diagnose:npl -- 0xWallet` now includes wallet income and its missing-data explanations.


## Risk Assessment and excluded positions

Aave v3 uses the pool's native, unweighted `totalCollateralBase` and `totalDebtBase` for the debt-versus-collateral rule. eMode-enabled collateral is recognized using its verified category bitmap and effective liquidation threshold, even when the reserve's ordinary-mode threshold is zero. An unreadable category leaves per-asset LLTV unknown and preserves the user's enabled collateral flag; it never replaces the native collateral total with zero. Health-factor risk labels remain independent of the Bad Debt classification.

The third sidebar section lists **Bad Debt** positions under the wallet owner's chosen rules: a Morpho/Euler collateral oracle that fails or returns zero, or wallet borrowing USD value strictly above pledged collateral USD value. Morpho direct markets check their configured collateral oracle even for supply-only deposits; Euler loans check held collateral receipts, and direct Euler lending deposits check accepted collateral routes with a positive liquidation LTV. Native quotes may use non-USD units. Independent display prices do not override a failed native oracle. Missing display USD prices alone remain unknown rather than proving an oracle failure or negative equity.

Excluded positions retain their balances, rates, market links and reasons in Risk Assessment, but contribute neither assets, debt nor interest to Wallet Overview totals and are omitted from recommendation requests/results. The unweighted collateral comparison excludes ordinary loan-token deposits and disabled collateral, including combined rows. Low health factor alone is not this rule. Exclusions are recomputed on refresh and removed if the oracle recovers or the borrowing/collateral condition clears. Receipt tokens remain excluded from wallet totals, so moving a deposit does not reintroduce its value through the wallet list. The raw API retains all positions and oracle checks; `diagnose:npl` reports excluded Bad Debt separately. The label is a user-defined dashboard classification, not an on-chain loss write-off.


Fluid T1 collateral valuation is independent of the wallet's borrowing balance. When an independent collateral USD feed is unavailable, a positive vault oracle ratio can be combined with the configured loan token's verified USD price even after all debt is repaid. Raw token decimals are applied to that ratio. Zero debt creates no borrowed-asset row or liquidation boundary; Supplied equals Net value, Monthly NPL equals monthly supply earnings, and a single supplied asset's position APR equals its effective Supply APR. These earnings enter Total NPL once. Missing reference prices/metadata, zero oracle ratios and smart-pool share ratios never create a guessed dollar price.


Borrowing alternatives with verified Available Liquidity below the active row's borrowed token amount are collapsed under **Lower liquidity markets**. The comparison uses normalized token quantities across matched networks, not USD values; equality stays in the main list. Both lists retain descending liquidity order, and the headline rate uses the main list. Unknown/invalid liquidity remains visibly unavailable rather than being assumed zero. Supply-only recommendations are unchanged, and opening a list never changes wallet totals.


Recommendations show the active borrowed token quantity beneath the borrowed asset and as **Amount to refinance** above each borrowing comparison. This is the full current debt-token balance, including accrued borrowing in the position snapshot; it is the same quantity used for the lower-liquidity grouping. Multiple collateral combinations repeat that same balance for comparison rather than allocating or summing it again. Supply-only recommendations have no refinance amount, and refreshed wallet balances update both displays.


Wallet Overview orders protocol/network cards and funded positions by current Net value, highest first; unknown values follow known values. Confirmed empty readers and zero personal deposits are grouped in the collapsed **Markets with 0 supplied assets** list below the active cards. A mixed Morpho card keeps funded deposits visible while zero-balance creator/curator/owner vaults move to the bottom list. Errors, incomplete discovery, unknown valuations, positive token balances priced at zero and debt-only positions remain visible. This grouping changes presentation only; the original portfolio data, financial totals, risk exclusions and recommendations are unchanged.


The Pendle section sorts nonzero, non-expired PT/YT holdings globally by wallet USD value, highest first, retaining network labels and placing unpriced holdings last. ### Five-minute liquidity tracker

[Track market liquidity alerts](.github/workflows/market-liquidity-monitor.yml) runs on `2,7,12,17,22,27,32,37,42,47,52,57 * * * *` (every five minutes, offset from the hour), on manual dispatch, and after tracker code changes. GitHub schedules can be delayed or dropped; this is not guaranteed real-time monitoring. The tracker reads entries with `rules.newLiquidityAdded` or `rules.liquidityWithdrawn` enabled from `analysis/wallet-history.json` and never changes user preferences.

- **`analysis/liquidity-alert-state.json`** stores exact per-token baselines, the last run event, the last confirmed scheduled run, and the last check/status for each wallet, chain, protocol and position. The first successful check only seeds a baseline. Changes update the baseline; only enabled directions generate notifications; failures keep the last successful amount. Disabling removes the baseline. Changing saved rules or re-enabling starts a fresh baseline.
- **`analysis/liquidity-alert-notifications.json`** appends increase and decrease notifications, each with a deterministic ID, wallet `address`, `network`, `protocol`, `positionId`, full `market`/`marketAddress`, token contract/symbol/decimals, `previousLiquidity`, `availableLiquidity`, `liquidityChange`, exact raw amounts, `previousCheckedAt`, `timestamp`, and block number. Decimal amounts are strings to preserve precision. Telegram delivery is handled by the separate delivery step described below; email delivery is not implemented.

Available liquidity is compared separately for each loan asset, never summed across token units. Borrowing positions monitor borrowed assets; deposit-only positions monitor their lending market. Morpho/Lista direct markets use accrued loan supply minus borrowing, Aave reserves respect virtual cash and borrow caps (including Horizon and GHO mint capacity), Aave v4 respects Hub/Spoke capacity, Compound uses base-token cash, Euler uses vault cash/caps, and Fluid uses resolver availability. Morpho/Lista/Spark Morpho vaults monitor allocated underlying markets and idle vault cash separately, without treating TVL as available cash. Savings products with no verified borrowing-liquidity metric are explicitly marked unsupported. Closed positions are inactive. Available liquidity may increase from repayments, accrued interest or cap changes as well as new deposits; the tracker detects the amount change, not its cause.

One workflow runs at a time. On-chain reads are pinned to one block per chain, shared market reads are reused, and changes use exact integer token units. Successful updates atomically commit baselines and notifications with `[skip ci] [skip render]`; branch conflicts reload current preferences/state and retry without overwriting other commits or duplicating notifications. Unreadable markets remain visible as errors in the state file and workflow summary; a run with failed/unsupported checks exits unsuccessfully after saving its status. No enabled rules means no RPC reads or repeated empty commits.

The workflow uses its built-in `GITHUB_TOKEN` with `contents: write`, so no new token is needed to write results. An external scheduler uses a separate repository-scoped Actions-write token only to dispatch the workflow. Public RPC fallbacks are configured for all five supported chains. Optional Actions secrets `ETHEREUM_RPC_URL`, `ARBITRUM_RPC_URL`, `PLASMA_RPC_URL`, `BASE_RPC_URL` and `BSC_RPC_URL` replace them; Render environment variables do not automatically become Actions secrets. Provider failures are not converted into zero liquidity. Local read-only check: `npm run track:liquidity -- --dry-run`. Publishing requires `--publish`, `GITHUB_TOKEN` and `GITHUB_REPOSITORY`.

The Alerts page distinguishes manual checks from native-cron and external-triggered checks. It displays a warning if no automatic trigger has been recorded, the last automatic check is over 15 minutes old, or a saved position lacks a recent successful check. Workflow `state: active` alone is not proof that GitHub is dispatching cron runs.


### Utilization threshold alerts

The same [market monitoring workflow](.github/workflows/market-liquidity-monitor.yml) checks saved `rules.utilizationAbove.enabled` preferences on its five-minute cron, manual dispatch, and tracker code changes. GitHub may delay or drop scheduled runs; it has produced multi-hour gaps in this repository. The Alerts page shows utilization monitoring status separately, including overdue scheduled checks.

- `analysis/utilization-alert-state.json` stores each enabled wallet/position/threshold, exact sampled block, last successful utilization per loan token/market, and scheduled-run heartbeat.
- `analysis/utilization-alert-notifications.json` stores `utilization-above-threshold` notifications with wallet address, chain, protocol, full market ID and contract, loan token, configured `thresholdPercent`, `previousUtilizationPercent`, current `utilizationPercent`, `utilizationChangePercentagePoints`, previous and current timestamps, and block number.

The condition is **strictly greater** than the threshold. The first successful check notifies if already above it; the previous reading and change are `null` because they are unknown. Subsequent above-threshold samples do not repeat the alert. Returning to or below the threshold re-arms it. Disabling removes the watch; editing a saved preference starts a fresh baseline. Errors retain successful baselines, old blocks cannot re-arm alerts, closed positions become inactive, and publishing rechecks current preferences to handle edits made during a run. State and notifications are committed atomically with conflict retries and deterministic notification IDs.

Morpho/Lista (including allocated vault markets) use accrued loan debt/supply. Aave v3/Horizon use reserve debt/(virtual underlying + debt), SparkLend uses actual underlying cash + debt, Euler uses borrows/(cash + borrows), Compound uses native Comet utilization, Aave v4 uses the native interest-model drawn/(liquidity + drawn + swept), and Fluid uses the official LiquidityResolver's accrued underlying-token total borrow/total supply (shared across vaults). Borrow caps, collateral TVL, withdrawal limits and wallet health factor are not utilization. A vault's unallocated idle cash has no utilization; unsupported savings products or unreadable data are explicit failures, never guessed zero. Multi-reserve positions are checked separately by token.

Local read-only check: `npm run track:utilization -- --dry-run`. Publishing: `npm run track:utilization -- --publish`, using the existing built-in Actions `GITHUB_TOKEN` and RPC secrets/public fallbacks. Utilization checks still run if a liquidity read fails; each metric has separate state and notification files. Only liquidity and utilization rules are monitored; the other saved alert checkboxes remain preferences.

### Telegram alert delivery

Liquidity messages contain only the title, wallet, chain, readable protocol/market name, asset symbol, available-liquidity change, increase or decrease, and Kyiv observation time. Morpho/Lista market names use their on-chain collateral and loan-token symbols. Full contracts, IDs, blocks and UTC timestamps remain in the JSON records.

The monitoring workflow delivers new liquidity and utilization notifications to the single Telegram destination configured in repository Actions secrets `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID`. Start the bot in Telegram first. Each workflow run (including cron-job.org dispatches) attempts delivery after both trackers, even if a tracker failed. It reads the latest GitHub files rather than stale checkout copies, so notifications created earlier in that run are available immediately. Credentials stay in Actions secrets and Telegram requests, never in GitHub JSON or application logs.

`analysis/telegram-deliveries.json` stores activation time (`enabledAt`) and per-notification delivery receipts. Alerts observed before activation are not replayed. A notification is sent only if its corresponding current wallet alert is enabled and its saved rule has not been edited after the observation; disabled/changed preferences are skipped. The original notification JSON files are unchanged. Changing the Telegram destination does not replay already delivered notifications.

Before sending, the workflow atomically claims a five-minute delivery lease using a non-forced Git update with conflict retries and fresh preference checks. After Telegram confirms a message, its message ID and sent timestamp are checkpointed before attempting the next notification. Sent/skipped receipts are not sent again. Failed sends remain pending for later runs with exponential backoff (5 minutes up to 1 hour), and Telegram `retry_after` is respected. Batches are bounded to ten attempted messages / about two minutes, and messages are spaced to avoid per-chat flooding. Failures are recorded using safe error codes (`unauthorized`, `forbidden`, `invalid_request`, `rate_limited`, `telegram_unavailable`, `invalid_response`, `network_error`), without raw API descriptions or chat details.

Telegram has no idempotency key for `sendMessage`. If it accepts a message but the response or GitHub checkpoint is lost, a retry after lease expiry can produce a duplicate. This is retryable delivery with persistent duplicate suppression, not an exactly-once guarantee. Delivery records retain stable notification IDs for diagnosing such duplicates. A failed connection test is recorded; rerun an explicit test after fixing credentials. Regular market notifications retry automatically.

To test, open [monitoring runs](https://github.com/Sberex/DeFiMon/actions/workflows/market-liquidity-monitor.yml), choose **Run workflow**, leave `source` as `manual`, and enable **Send a one-time Telegram connection test** (`telegram_test: true`). A successful test creates a `kind: test`, `status: sent` receipt and sends “DeFiMon · Telegram delivery test”; it does not create a fake market alert. The external scheduler's existing request body needs no changes and does not send connection tests every five minutes.

Read-only local check: `npm run deliver:telegram -- --dry-run`. Publishing is `npm run deliver:telegram -- --publish` and requires GitHub Contents write credentials plus both Telegram secrets. Missing or invalid secrets fail the delivery step visibly; the tracker results already stored in GitHub are retained. Delivery status JSON is linked from Wallet Overview → Alerts.

### Leveraged Borrowing Strategy Search

Below the regular Market Discovery search, a separate search restricts collateral to configured **Savings stablecoins with `_intrinsicOracles`**, and debt to configured **Stablecoins**. Prefix autocomplete and Any asset work independently on both sides; Any asset still respects these categories. `/api/leveraged-strategies` validates these choices and reuses the ordinary discovery cache, market readers, partial-coverage reporting, and shared concurrency limit.

Results require a verified current intrinsic APR strictly above the borrowing APR. Missing intrinsic rates, borrow rates or fixed LLTV, deposit-only products, unconfigured contracts, and pools requiring additional supply/debt assets are excluded. Identity uses configured chain and contract addresses. Curve markets without a fixed LLTV cannot use this model.

At target health factor **1.02 or higher**, debt/collateral `r = LLTV / 1.02`, capped by verified maximum entry LTV when available, equity/collateral `= 1 − r`, and net equity APR `= (total Supply APR − Borrow APR × r) / (1 − r)`. Total Supply APR includes native protocol supply interest, verified intrinsic yield and eligible Merkl supply incentives. The qualification test compares intrinsic yield with effective Borrow APR after verified Merkl incentives. This assumes constant prices, rates and collateral factors, excludes unverified rewards, fees and slippage, and does not guarantee sufficient capital, liquidity or execution eligibility. Results show the original market liquidity and LLTV, group by chain, and sort by modelled APR descending, with 50 results per chain initially and Show more. Strategy markets with verified available liquidity below $0.01 are collapsed below the main list, retaining chain grouping and APR sorting. Exactly $0.01 and unavailable USD valuations remain in the main list. The regular discovery form and liquidity sorting remain independent.


### Merkl incentives in Market Discovery

Both discovery forms include independently verified public Merkl programs. Borrow incentives reduce effective Borrow APR; supply incentives increase total Supply APR. Protocol rates remain visible separately, alongside reward rates, campaign links, expiry and netting conditions. The leveraged model uses these effective rates, including a negative effective borrow APR when verified incentives exceed protocol interest. APR remains a simple annual rate; net Borrow APY subtracts Merkl’s separately reported reward APY from protocol APY, rather than relabelling APR as APY.

The service queries LIVE opportunities by chain with bounded pagination and a five-minute cache, checks active campaign dates and recent rate timestamps, and validates public eligibility. Supported programs are Aave v3/Horizon `AAVE_NET_BORROWING` and `AAVE_NET_LENDING`, and simple Fluid `FLUIDVAULT_BORROW` / `FLUIDVAULT_COLLATERAL` campaigns. Aave receipt-token underlying, pool identity and native aToken/variable-debt-token membership are verified on-chain at the market snapshot block. Matching uses contracts, chain, market and lending side, never symbols or names. Private/allowlisted/blacklisted, custom-scoring, forwarded, unknown-condition, conflicting, expired and unreadable campaigns are excluded and reported through coverage.

Discovery assumes the displayed pair is the complete position. Aave rewards are included only when the opposite asset does not reduce the campaign’s net exposure; balance-dependent cases are conservatively omitted rather than promising the headline rate. Other positions in the same wallet can reduce eligibility. Smart multi-token Fluid vault rewards and unsupported campaign types are omitted. Failure to load incentives preserves native market data and explicitly reports that unverified incentives are excluded. These changes do not modify wallet reward balances, wallet NPL, or the separate Recommendations alternatives search.

### Aave eMode in leveraged strategy modelling

Aave discovery reads all eMode categories from each chain’s official address-book `UI_POOL_DATA_PROVIDER.getEModes(provider)` at the same block as market rates. Native pool reserve IDs establish collateral and borrowing bitmap membership. Categories with a zero-LTV flag for the collateral are excluded. Both the collateral and selected debt must qualify; token symbols and category labels never establish eligibility. Failed enumeration or reserve checks produce partial coverage and retain only a verified standard borrowing mode. A standard zero LTV cannot be used to model a new loan.

The strategy evaluates each eligible standard/eMode configuration and displays the highest modelled APR, using Merkl-adjusted borrow APR exactly once. For each mode, `r = min(LLTV / 1.02, maximum entry LTV)` and `APR = (total Supply APR − effective Borrow APR × r) / (1 − r)`. The UI shows the selected eMode, its LLTV and entry LTV, debt/collateral ratio, actual modelled health factor and any entry-LTV cap. If the cap prevents entering at exactly 1.02, the model uses a higher health factor. Aave eMode must be enabled to obtain the displayed eMode terms. Ordinary Market Discovery lists each verified standard/eMode borrowing configuration as a separate row, displaying its own LLTV and maximum entry LTV, with the eMode ID and label in the market information. Zero-LTV standard configurations are omitted. Variants refer to the same underlying pool, so their liquidity is shared and must not be summed.

`/api/market-discovery` expands the raw cached Aave pairs into these verified mode variants; the frontend handles expansion idempotently. `/api/leveraged-strategies` still selects the best verified mode for each pair from the same unexpanded cache. Discovery includes potential eMode-only collateral even when the standard reserve collateral setting is disabled or its threshold is zero, then emits it only after positive entry-LTV and collateral/borrow membership checks. Recommendations matching retains its existing standard-mode eligibility checks.
